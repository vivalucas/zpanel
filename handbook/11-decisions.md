## Docker socket 权限须验证实际服务身份

**日期**：2026-10-25；**状态**：已随 1.2.7 发布并完成 m5 验证。

容器内安装 Docker CLI、宿主 Docker 正常或 Compose 配置 `group_add`，都不能单独证明管理功能可用。`su-exec zpanel` 会按容器 `/etc/group` 重置补充组；入口只为已挂载 socket 且启动组列表已包含的 socket GID 建立用户组成员关系，不继承其他附加组，不以 root 服务或放宽宿主 socket 权限替代。判据包含启动进程的主组（例如 root 的 GID 0），不把它误写为仅能识别显式 `group_add`。

BusyBox `addgroup -g` 有小于 Linux 合法 GID 范围的编译上限；新组使用经过校验的数值与安全生成名称写入容器组文件，现有组复用。Docker 是可选能力，组准备失败时告警并继续站点启动，基础配置/数据初始化仍失败即退出；不能仅靠 `set -e`，须显式处理函数在条件表达式中执行时的错误。回归覆盖大 GID 和失败继续，实际 BusyBox/su-exec 仍须隔离验证。

切换前在正式镜像隔离验证，切换后检查实际进程 UID/Groups，并以该用户读取 Docker 和验证专用临时容器动作；其他生产容器不可作为启停测试对象。1.2.7 镜像内置修复；旧 1.2.6 的临时只读入口挂载须在升级时移除。具体生产状态见 [01](01-current-status.md)。

## 决策 3：README 与产品语言集合保持一致

**日期**：2026-05-20

**状态**：已采用

**替代关系**：无

**类型**：产品 / 前端 / 文档

**背景**：

用户希望 ZPanel 像 DashCat 一样提供多语言 README，并要求产品本身也支持同样的语言。这个需求包含两层：一是语言入口和产品 i18n 框架，二是每种语言的真实翻译质量。

**考虑过的方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 继续只支持中英文 | 不增加新的 README 和产品语言 | 维护成本低 | 不符合项目多语言目标 |
| B. 只做 README 多语言 | 产品 UI 仍只保留中英文 | 文档层面容易完成 | 产品体验和文档承诺不一致 |
| **C. 语言集合统一，真实翻译分阶段完成** | README 和产品都支持 11 种语言，先完成框架和 key 对齐，后续逐语言翻译 | 架构清晰，便于持续补齐 | 第一阶段非中英语言还不是最终体验 |

**最终选择**：

选择 C：README 和产品语言集合保持一致，均支持简体中文、English、日本語、한국어、Deutsch、Français、Español、Português do Brasil、Italiano、繁體中文、Русский。当前先完成语言框架、locale key 对齐、中英文优化和文档说明；非中英真实翻译版后续逐个补齐。

**依据**：

- 用户明确要求 README 和产品本身都支持这些语言。
- 先把 locale key 对齐，可减少后续翻译工作中的技术噪声。
- 翻译质量需要语境、术语、UI 长度和地区用语校对，不适合一次性草率宣布完成。

**实现原则**：

- README 多语言和产品 UI 多语言都要有清晰入口。
- 产品 locale 文件必须 key 完整，不能因为切换语言导致运行时缺失文案。
- 中英文作为第一批真实可用文案维护。
- 其他语言在真实翻译完成前只作为基线文案，不对外宣称已经完成母语级翻译。

**已知不足**：

- 日语、韩语、德语、法语、西班牙语、巴西葡萄牙语、意大利语、俄语目前使用英文基线文案。
- 繁体中文目前使用简体中文基线文案。
- 真正翻译版仍需逐语言完成术语表、母语级翻译、界面长度检查和实际交互校验。

**后续触发条件**：

- 发布面向多语言用户的正式版本前，至少应完成目标语言的真实翻译或在发布说明中清楚标注翻译状态。
- 新增用户可见文案时，必须同步更新所有 locale key。
- 每完成一种真实翻译，需要进行桌面和移动视口的 UI 文案溢出检查。

**相关文件**：

- `README.md`
- `README*.md`
- `src/locales/`
- `src/locales/index.ts`
- `src/store/modules/app/helper.ts`
- `src/utils/defaultData/index.ts`
- `09-current-plan.md` 中的 ADR-004
- `11-decisions.md` 中的 2026-05-20（多语言 README 与产品本地化框架）

**后续补充**：

- 真实翻译版完成后，在本条决策下追加各语言完成状态。

## 决策 2：面板功能直接进入 ZPanel 开源版

**日期**：2026-05-20

**状态**：已采用

**替代关系**：无

**类型**：产品 / 安全 / 架构

**背景**：

用户要求将导航、个性化、多账号、图库和 Docker 管理等面板能力直接开放给所有用户。ZPanel 不在当前阶段设计付费授权系统。

**考虑过的方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 维持功能限制 | 保留标准版 / PRO 版差异 | 保留功能分层 | 与 ZPanel 当前开源目标冲突 |
| B. 等待长期插件系统 | 把 PRO 功能推迟到未来 V2 / 插件化后实现 | 架构更从容 | 短期不能解决用户需求 |
| **C. 直接开源化实现** | 按公开描述重新实现并开放给所有 ZPanel 用户 | 用户价值明确，维护边界清晰 | 需要补安全提示和后端验证 |

**最终选择**：

选择 C：公开 PRO 功能表中的面板能力直接进入 ZPanel 开源版，不引入付费限制，不复制闭源代码，也不实现商业商城 / 授权后台。

**依据**：

- 用户明确要求“在我们这个版本里面实现它所有的这些功能”。
- 功能表描述的是能力，不是闭源代码本身。
- 当前代码已有用户管理、文件管理、样式配置、导入导出等基础，适合第一版增量实现。
- ZPanel 当前目标是独立维护和自托管可用性，不是商业授权平台。

**实现原则**：

- 配置类能力优先复用 `system_setting` 和既有用户配置。
- 多账号快速切换先做浏览器本地能力，不新增服务端会话管理表。
- Docker 管理只对管理员开放，并明确部署环境权限要求。
- 备份迁移只维护 `.zpanel.json`。

**已知不足**：

- Go 后端尚未在当前环境完成编译验证。
- Docker 管理未在真实 Docker 环境完成操作验证。
- 自定义 JS / CSS 缺少一键恢复或安全模式。
- 登录验证码请求中当前复用了 `email` 字段传 `captchaId`，后续可重命名以减少歧义。

**后续触发条件**：

- 发布 release 前必须完成 Go 编译、后端启动和 Docker 管理实机验证。
- 如果未来做插件 / 应用市场，需要重新评估 Docker 管理和公共图库是否应插件化。
- 如果用户反馈自定义 JS / CSS 误配置导致无法进入系统，应优先实现安全模式或配置重置入口。

**相关文件**：

- `09-current-plan.md` 中的 ADR-003
- `11-decisions.md` 中的 2026-05-20（PRO 功能开源化第一版）
- `service/api/api_v1/system/docker.go`
- `src/features/settings/Docker.tsx`
- `src/features/settings/Appearance.tsx`

**后续补充**：

## 决策 5：管理员级安全能力的边界认定

**日期**：2026-05-22

**状态**：已采用

**替代关系**：无

**类型**：安全 / 产品

**背景**：

第二轮代码评审中，多个安全相关的能力需要判定是 bug 还是设计意图：customJs/CSS 注入、favicon 获取（潜在 SSRF）、默认密码、静态文件无鉴权、Token 明文存储。

**讨论过程**：

项目支持公网和内网两种部署场景。部分用户直接部署在公网服务器上通过域名访问，部分用户部署在家庭内网的 NAS 上。需要结合两种场景判断每个安全项的性质。

**最终判定**：

| 能力 | 判定 | 理由 |
|------|------|------|
| customJs/CSS 直接注入 DOM | 设计意图 | README 明确列出"在线编辑自定义 CSS 和 JavaScript"为功能。管理员自定义能力，文档已提示风险。 |
| GetSiteFavicon 获取内网地址 | 设计意图，现有白名单边界见后续补充 | NAS 内网服务图标是正常用例；管理员须显式列出私网源，普通账号只访问公网。 |
| 默认密码 12345678 | 设计意图 | 开源项目，源码公开，密码保密无意义。README 已提示"首次登录后请立即修改默认密码"。 |
| /uploads 静态文件无鉴权 | 设计意图 | 自托管面板，上传的图标和壁纸需要被浏览器直接访问。 |
| Token 明文存 localStorage | 标准做法 | SPA 项目标准方案，安全重点应放在防 XSS 而非加密存储。 |

**依据**：

- 项目 README 已将 customJs/CSS、Docker socket、公开访问列为"高权限能力"并明确提示风险。
- 这些能力的设计意图是给管理员使用，不是暴露给任意用户。
- 自托管面板的安全模型与 SaaS 不同，管理员即部署者。

**已知不足**：

- customJs 注入无 CSP 防御纵深。
- 私网 favicon 已通过精确源名单、重定向和 DNS 实际连接校验限制；真实 NAS 环境尚未实测。
- 这些不足在当前阶段可接受，后续如需加强可单独补充。

**后续触发条件**：

- 如果项目未来支持多租户或非管理员用户可触发这些能力，需要重新评估。
- 如果用户反馈公网部署时被扫描内网，应优先给 GetSiteFavicon 加 IP 白名单或禁用选项。

**⚠ 注意**：以上判定主要基于 AI 对项目场景的理解，可能不完全准确。如有不同意见请修正。

**相关文件**：

- `src/app/App.tsx`（customJs 注入）
- `service/api/api_v1/panel/itemIcon.go`（GetSiteFavicon）
- `service/initialize/database/connect.go`（默认密码）
- `service/router/router.go`（静态文件）
- `src/store/modules/auth/helper.ts`（Token 存储）

## 决策 6：全新项目无需向后兼容

**日期**：2026-05-22

**状态**：已采用

**替代关系**：无

**类型**：架构 / 安全

**背景**：

第一轮评审中，密码加密采用了 bcrypt + MD5 回退的兼容策略，以支持旧用户迁移。经确认，ZPanel 是全新项目，没有其他项目迁移过来的老用户。

**最终选择**：

移除 MD5 密码回退逻辑。bcrypt 失败时直接报错，不再降级。`VerifyPassword` 中的 MD5 验证分支也一并移除。

**依据**：

- 没有旧用户需要迁移。
- MD5 对密码哈希来说极弱，保留回退逻辑增加攻击面而无收益。
- 全新项目可以干净地使用最佳实践，不需要历史包袱。

**⚠ 注意**：此决策基于"项目没有老用户"的前提。如果未来发现有旧数据导入场景，需要重新评估。

**相关文件**：

- `service/lib/cmn/base.go`（PasswordEncryption、VerifyPassword）

## 2026-09-12 评审修复的长期取舍

**状态**：已采用；依据用户明确授权落实文档与代码修复优化，方案见 ADR-20260912。

1. 默认不信任代理，显式填写可信地址；不恢复旧全网信任，防止通过伪造转发头绕过限流。
2. 在既有 URL 数据未迁移前，资源引用从业务数据按需核查，不能依赖空引用表。适用于个人服务器规模；多副本协调和完整增量索引后续单独设计。
3. 导入使用服务端事务和持久幂等收据，避免前端补偿请求在断网时失效；覆盖必须显式选择，默认追加。
4. 配置导出不承诺携带二进制图片，完整备份使用 conf/data；UI 明确说明此边界。
5. 导航跳转只允许网页协议和相对地址，阻断导入内容中的脚本 URL；如果未来需要 ssh 等原生客户端协议，应显式评估和增加白名单，而非开放任意协议。
6. 当前 Git 已跟踪 handbook，本轮保留现状。早期“只在本地忽略”的要求记为历史取舍，未擅自删除跟踪或改写 Git 历史。

## 发布数据一致性

发布前后 SQLite 按 schema 和逻辑行核对。GORM 启动迁移会重排 sqlite_sequence 的隐含 rowid，1.2.8/1.2.9 同条件副本已精确对照；仅该内部表排除无业务语义的隐含行号，name/seq 仍严格比较，业务表行号规则不变。不能忽略整个计数表或以“启动正常”代替数据验证；清单格式变化须重新生成前后两份，拒绝混用。

## 当前前端决策

查询首次失败后 refetch 会先清空 error，不能仅用瞬时 error 决定错误卡片是否挂载。显式重试期间保留本次错误与按钮加载状态，完成后由新结果接管；权限拒绝的旧数据在此期间继续隐藏，不将重试开始视为权限恢复。Docker 回归以挂起请求验证此边界，不靠增加超时掩盖卡片卸载。

图标不自动去底或统一 cover 裁切；旧白色可能是默认值或用户选择，不能按色值清空。新增空背景使用磨砂，旧显式底色保留，参数见 [UI 规范](../docs/ui-design.zh-CN.md)。固定 flex 底座避免纵图撑高 grid 隐式轨道后裁切；回归检查横竖图两端的实际像素，不能只断言 contain。换类型/地址时重置图片失败状态，编辑预览共用组件，不新增持久化字段。

图标磨砂先写 `-webkit-backdrop-filter`、后写标准属性。反向顺序会让固定构建工具仅保留前缀，本机 Chromium 忽略该别名而无模糊。回归须检查生产构建后的 computed style；源码有声明或底色半透明不能证明磨砂生效。其他既有玻璃规则的同类顺序未在本轮图标范围内统一调整。

2026-10-24 用户确认全页评审建议后，沿用壁纸桌面和设置悬浮窗口，玻璃材质扩展至菜单/弹窗等操作浮层；文字密集表面使用厚磨砂并提供低透明度回退。手机开关保持同行，长弹窗固定动作区，配色等低频项折叠，保存范围和已有配置不变。控件语义与排序播报同步本地化，不能以视觉标签已存在代替输入控件名称。

异步上传结果按字段草稿版本写回，不仅比较地址是否相等；用户 A→B→A 仍算新编辑。暂时刷新失败可保留本会话缓存，鉴权拒绝不可保留；保存成功先更新缓存，重取失败也不能恢复旧表单值。搜索默认项按完整对象匹配并为旧值回退 URL，不为重复 URL 新增实体或迁移。只改资料头像可保留既有非空昵称，新昵称仍执行原长度约束，不改写存量默认值。

## 配置、安全权限和私网图标的当前边界

## 前端事件的生命周期与确认边界

**日期**：2026-10-23；**状态**：按用户授权实施，专项证据及验收见 [16 前端事件检查](16-frontend-event-review.md)。

- 页面发起的请求同时绑定发起会话和组件生命周期，显式匿名登录也不能在离页/切账号后接受旧响应；调用方取消信号与页面信号均有效，合并监听在完成后清理。不依赖新的 AbortSignal 静态便利方法。客户端取消不代表服务端写入回滚。
- 确认框属于发起页面，离页销毁，旧确认不得操作新页面或账号。已明确确认放弃草稿的账号转换必须先同步放行离页拦截，再改变会话并导航，避免 React 状态更新前仍被旧 blocker 拦住。
- 上传完成前，依赖上传地址的外观、资料和项目表单不能提交；保存期间不接收新上传。异步 favicon 写回前比较目标 URL、图标类型和草稿地址。备份等本地异步读取以最后一次选择为准，确认时冻结本次预览。
- 受草稿保护的内部入口使用 Router 导航；原生外部导航保留修饰键/中键。编辑结束按稳定项目 ID 找回当前按钮，不能假定跨分组移动后旧 DOM 仍存在。
- 语言失败回退也必须服从最新选择；安全模式按本页是否曾执行自定义脚本决定是否刷新，不能用当前脚本是否为空推断旧副作用已消失。
- 交互缺陷须复核实际回调和第三方控件行为，不能仅以按钮未显示 disabled 判定可取消；确认问题、加固和模拟事件时序局限分别记录。
