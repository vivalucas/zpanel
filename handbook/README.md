- 用户：项目根 README.md → 必要的使用指南。

- AI：[根 AGENTS.md](../AGENTS.md) → 01 当前状态 + 本文件索引；首次接手或方向变化再读 00。
- 功能读 02，UI 读 03 并查相似页面，架构读 04，数据读 05，接口读 06。
- 环境读 07，部署读 08，计划读 09，验证/评审读 10，旧设计或历史问题查 11，外部服务读 12，操作指南读 13。

首次开发读下方“开发与协作”“日常收尾”；同步、评审、整理分别查对应章节。无关历史、长参考和原始样本不全文读取。任务模式与核心边界以根 AGENTS.md 为准。

## 14+ 扩展

1. 先查现有内容，避免重复；新文件注明用途、状态、范围、依据和维护时机，登记下表。
2. 编号按文件与索引的历史最大值递增；多人扩展先协调，不复用旧编号。删除专题后保留“原编号、主题、已移除”一行记录。
3. 标准文档只保留摘要和链接。结束后回写长期约定，按价值压缩过程，不按对话逐次建文件。

## 事实与文档分工

当前约定直接更新，过期内容可删除；重要原因和经验留 11，完整修改历史交 Git，不另写开发流水账。未解决问题、未提交的唯一工作必须保留。

代码说明当前实现，已确认需求说明预期；发现不一致时辨认是文档过期还是 bug。版本以清单和锁文件为依据，数据结构以模型和迁移为实现依据，文档补充业务语义，不手抄全部可生成细节。

根 README.md 维护产品介绍、启动和使用入口；根 AGENTS.md 维护核心规则；本文件维护导航和流程；CLAUDE.md 只导入。各入口按上述阅读路线相连，不复制多份同义规范。

## 检查工具

在业务根目录运行 `python handbook/tools/check_docs.py`；macOS 可用 python3，Windows 可用 py，uv 项目可用 uv run python。无需为了检查强制安装 Python；环境不可用就做人工检查并说明。

工具只读检查标准文件、Claude 导入、常见本地 Markdown 文件链接、00/01 初始化和篇幅。不验证业务事实、外网、锚点或 AI 是否遵守。`--strict-init` 将 00/01 的占位内容视作错误，不要求不适用文件填满。工具不自动删文件、不联网、不执行 Git。

## 开发与协作

按入口规则检查代码、现有修改、分支和锁文件，明确“需求—现有实现—本轮改动—验证方式”后实施。

小修复简述即可；跨模块、数据结构或长期行为变化先写精简计划。需求内明确的实现直接处理；改变产品含义或破坏兼容的重大取舍先讨论，已授权事项不重复确认。

多人并行在 01 登记范围、负责人和依赖；共享文件重叠时协调顺序。文档登记不是文件锁，不覆盖其他任务的未提交内容。

## Git 与跨设备同步

### 项目策略

- 分支：项目日常开发、提交和推送仅使用 `main`，不创建其他人工分支或工作树。偏离 `main` 时先核对历史与工作区，再安全整合回 `main`。
- 提交、推送：默认由用户指令触发。
- 开工同步：允许 fetch；仅开发或已授权同步任务，在工作区干净、upstream 明确且只落后时允许快进。只读评审和文档整理不自动合并代码。
- 自动提交推送：默认关闭。仅在用户明确开启后更新提交推送策略，并记录适用范围；不包含版本升级、标签或 Release。
- 推送触发的外部动作：已检查仓库工作流：main 分支 push 运行 CI；发布与容器推送由 v* 标签或手动触发。 GitHub 外部集成未验证；本轮仅文档同步，不授权后续自动提交或发布。

### 开工检查

1. 检查 `git status --short --branch`、当前分支和 upstream；无 Git 仓库时说明，不假装已经同步。
2. 有远端时 fetch 对应 remote，成功后比较当前分支与 upstream。fetch 失败或离线则报告“远端状态未知”。
3. 仅在开发或用户授权的同步任务中，干净且只落后时，可对已核实的 upstream 执行 `git merge --ff-only @{upstream}`；PowerShell 中将 `@{upstream}` 用单引号包裹。远端有新提交不能直接覆盖本地。
4. 工作区有修改时不自动 stash、reset 或清理。历史分叉时先识别双方改动和给出整合方案，取得本次整合授权后再处理；不自动 rebase、合并或强推。
5. 没有 upstream、存在多个可能的远端、分离 HEAD 时，先定位或询问缺失目标，不猜测推送目的地。

Git 看不到另一台设备尚未推送的工作。离开前“收工同步”，或明确开启自动提交推送；依赖目录、运行数据库和真实 `.env` 不通过 Git 换机。

### 提交与推送

“推送 / 收工同步”包含提交本轮必要改动并推送当前分支。先看 diff，只暂存归属明确的文件或片段，不夹带无关修改；已有提交属于授权范围时可直接推送。

推送前重新 fetch 并检查分叉，确认目标为已知的 `origin/main`；upstream 异常时先核实，不猜测推送目的地。推送后核实远端目标提交，失败如实报告。

未经明确授权不强推、不重写已共享历史、不删除分支。提交说明描述一个清晰目的，可用 feat / fix / docs / refactor / chore 前缀。

### 版本与部署

普通提交推送不修改版本号、不打标签、不创建 Release。用户要求发布版本时，先检查项目版本来源和变更范围，再同步必要版本、发布说明、验证和标签。操作生产环境按用户具体授权执行。

如果 push 会触发部署等外部动作，而用户只授权代码同步，先说明该绑定并确认外部动作范围；不擅自改 CI 来绕过它。用户已明确授权该项目的推送部署流程则按约定执行。

## 日常收尾

按本轮需求逐项核对，检查 diff 和关联路径。验证与影响匹配：文案修改不必全项目测试，数据或核心逻辑改动需覆盖边界与回归。

UI 改动优先复用主题和页面范式，检查导航、主要动作、字段含义、空/错/加载/禁用状态及操作后的反馈。能运行时实际检查界面；只能静态检查则明确说明，不将构建通过等同于界面验收。

跨平台项目分别报告 Windows、macOS、Ubuntu 的验证情况；本机通过不代表其他平台通过。验证记录包含对象、代码基线（含未提交改动）、方法与结果、未覆盖范围；命令和长期回归脚本可链接，临时日志不当作永久证据。

更新有变化的状态与相关约定。简短结果在对话报告即可；需要跨对话继续、存在风险或验收缺口时留入状态。只有重要问题或专项评审才建立报告。多个需求在同一轮开发时，结束前对累计改动做一次整体收尾，检查它们之间的交互影响，不能只检查最后一个修改。

## 专项评审（默认只读）

用户要求“全面评审 / 检查老项目”时，先整体理解项目并声明本轮范围和基线；阅读相关实现、测试和约定，逐条复核发现，避免只凭关键词判断 bug。

输出四部分：项目理解、确认问题、待验证问题、体验建议。每项问题包含触发条件、位置、影响、证据、建议及优先级；体验建议不能冒充 bug。

默认不改代码或项目文档；用户要求保存报告时简短结论写入 10，复杂报告可建立 14+ 评审专题并登记导航，要求修复后进入开发流程。只读分析不运行会改用户配置、数据库或外部资源的验证；需要时先准备隔离环境并说明边界。

自查与独立评审分别标识。不默认无限多轮全量评审；按范围完成检查、给出剩余风险即可，不声称“没有任何 bug”。

## 上下文维护

每次更新顺手整理对应章节。单份当前文档过长、重复结论出现或阶段结束时，再集中整理；不因字数警告机械删减。

1. 确认工作区中的文档改动归属，读取导航、状态和相关实现依据。
2. 当前约定只保留有效内容，09 计划明确区分未实施、部分实施、完成与放弃。
3. 已完成计划提取长期决策，清理无价值过程；已解决评审问题保留必要经验或回归证据。
4. 保留未解决问题、活跃交接、用户约束和必要复现信息。不确定的内容标明待复核及依据，不能仅压缩成无信息的一句话。
5. 原始样本、完整评测输出和参考资料单独管理；导航只保留用途和摘要，不为了缩短上下文销毁有用数据。
6. 调整路径同步修复引用，运行文档检查。集中维护只改文档，不顺手修改业务实现；发现矛盾在结果中说明。

完整变更历史主要交给 Git。未提交、未推送且不可恢复的重要工作不得被当作旧历史丢弃。无需建立无限归档库；确需保留的历史摘要按主题存放、标明失效原因。

## 信息保护

敏感信息按根规则处理，样本用最小脱敏数据。发现凭据泄露时说明受影响位置，按授权处理轮换，不在文档再次复制凭据。

跨设备共享必要的规则、清单、锁文件和脚本；个人工具设置、缓存和会话记录按需忽略，不把整个规则目录一概加入忽略。
